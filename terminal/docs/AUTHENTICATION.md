# Authentication and execution contract

## Supported Microsoft mechanisms

- [Connect-MgGraph](https://learn.microsoft.com/en-us/powershell/module/microsoft.graph.authentication/connect-mggraph?view=graph-powershell-1.0): delegated `-UseDeviceCode -ContextScope Process` with explicit read scopes. Initial sign-in omits optional `-TenantId`; authenticated context supplies identity. Startup A uses displayed Audit read scopes only by explicit selection; G stays User.Read. Standard action runs never sign in again. No token extraction, user/password form, secret file or app registration.
- [Get-MgContext](https://learn.microsoft.com/en-us/powershell/module/microsoft.graph.authentication/get-mgcontext?view=graph-powershell-1.0): local account, tenant, environment, authentication type and scopes are checked. The toolkit does not print or export the full authentication context.
- [Connect-ExchangeOnline](https://learn.microsoft.com/en-us/powershell/module/exchangepowershell/connect-exchangeonline?view=exchange-ps): PowerShell 7 `-Device` in the documented default parameter set, with no other sign-in arguments; returned identity is verified rather than assumed from a login hint. The app requires PowerShell 7.4+ and ExchangeOnlineManagement 3.7.0+ for collection. Device-code mode is never a fallback after denial.
- [Get-ConnectionInformation](https://learn.microsoft.com/en-us/powershell/module/exchangepowershell/get-connectioninformation?view=exchange-ps): active REST connection, `TenantID` GUID, `UserPrincipalName`, token status, workload, module prefix and command-origin binding are verified. `Organization` is a certificate/managed-identity input, not used as proof of a delegated tenant name. Missing/ambiguous metadata fails closed with reconnect instructions.
- [Connect-IPPSSession](https://learn.microsoft.com/en-us/powershell/module/exchangepowershell/connect-ippssession?view=exchange-ps): no documented `-Device` switch. This app **never calls it**. Only an existing approved matching Purview session can be used; otherwise those sources are unavailable.

Device-code login still requires an approved web browser/device for Microsoft's verification page. It avoids the local redirect/listener that [MSAL system-browser authentication](https://learn.microsoft.com/en-us/entra/msal/dotnet/acquiring-tokens/using-web-browsers) may use. The toolkit does not control Microsoft page behavior or tenant policy. A device-code denial remains a denial; there is no retry using a different identity or auth mode.

## Scope sequencing

1. Startup A explicitly requests the displayed already-approved Audit read scopes in one device-code flow, then proceeds directly to the tenant-bound `AUDIT` confirmation. G (default) requests only User.Read, E uses Exchange `-Device`, and R reuses an existing session. G/E/R display verified tenant/account and proceed to the menu without another confirmation. No organization API is called merely to discover tenant identity.
2. Audit displays the exact authenticated tenant/operator and concrete 46-source scope. One exact `AUDIT` response authorizes those organization-wide reads; blank/mismatch cancels. The matching tenant ID is still passed to the underlying guarded collector. No separate GUID-copy or Y prompt is required. All component sessions must still match the verified tenant/account.
3. Standard Audit and Pull Logs use only existing approved sessions/scopes. They never reconnect, grant consent, or ask repeated provider/scope questions. Missing permissions/modules/providers become source-level gaps. Identity-only G may collect no configuration sources; choose startup A only when its exact displayed permissions are already approved. A new consent request means stop.
4. Pull Logs retains exact target/date authorization and separate Defender/beta opt-ins. Required Graph reads remain AuditLog.Read.All, Directory.Read.All, IdentityRiskEvent.Read.All, plus ThreatHunting.Read.All for opted-in Defender. Missing scopes are skipped; no broader fallback. Direct connection helper APIs remain available for separately deliberate approved setup, but are not invoked by standard collection actions.
5. Source access and tenant/account binding are revalidated during collection. Menu S saves the latest in-memory result explicitly without another collection or sign-in; blank cancels and no files are created by default. No external writes, role activation or automatic permission grants are attempted.

Operators must only request access already approved by their organization and must stop at any unexpected consent prompt. This documentation is not permission to grant access.

## Device-code instructions not visible

The connector renders authentication success-stream output directly with `Out-Host`, before its callers capture the resolved session. Graph device instructions can otherwise be swallowed by `Out-Null` or variable assignment while authentication waits ([upstream behavior report](https://github.com/microsoftgraph/msgraph-sdk-powershell/issues/2798)). A delayed synthetic prompt regression covers this boundary without authenticating or producing a usable code. Device mode does not launch a browser popup. If updating a stalled session, cancel with Ctrl+C and start a fresh interactive PowerShell process so the previously imported toolkit module is not reused. Do not share codes in reports or enable debug/transcript capture to troubleshoot. This display fix does not change requested scopes, consent, policy enforcement, account selection or session checks.
