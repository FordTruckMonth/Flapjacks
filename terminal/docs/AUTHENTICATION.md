# Authentication and execution contract

## Supported Microsoft mechanisms

- [Connect-MgGraph](https://learn.microsoft.com/en-us/powershell/module/microsoft.graph.authentication/connect-mggraph?view=graph-powershell-1.0): delegated `-UseDeviceCode -ContextScope Process` with explicit read scopes. The initial `User.Read` sign-in omits optional `-TenantId`; subsequent action sign-ins pass the tenant obtained from the confirmed authenticated context. No token extraction, user/password form, secret file or app registration.
- [Get-MgContext](https://learn.microsoft.com/en-us/powershell/module/microsoft.graph.authentication/get-mgcontext?view=graph-powershell-1.0): local account, tenant, environment, authentication type and scopes are checked. The toolkit does not print or export the full authentication context.
- [Connect-ExchangeOnline](https://learn.microsoft.com/en-us/powershell/module/exchangepowershell/connect-exchangeonline?view=exchange-ps): PowerShell 7 `-Device` in the documented default parameter set, with no other sign-in arguments; returned identity is verified rather than assumed from a login hint. The app requires PowerShell 7.4+ and ExchangeOnlineManagement 3.7.0+ for collection. Device-code mode is never a fallback after denial.
- [Get-ConnectionInformation](https://learn.microsoft.com/en-us/powershell/module/exchangepowershell/get-connectioninformation?view=exchange-ps): active REST connection, `TenantID` GUID, `UserPrincipalName`, token status, workload, module prefix and command-origin binding are verified. `Organization` is a certificate/managed-identity input, not used as proof of a delegated tenant name. Missing/ambiguous metadata fails closed with reconnect instructions.
- [Connect-IPPSSession](https://learn.microsoft.com/en-us/powershell/module/exchangepowershell/connect-ippssession?view=exchange-ps): no documented `-Device` switch. This app **never calls it**. Only an existing approved matching Purview session can be used; otherwise those sources are unavailable.

Device-code login still requires an approved web browser/device for Microsoft's verification page. It avoids the local redirect/listener that [MSAL system-browser authentication](https://learn.microsoft.com/en-us/entra/msal/dotnet/acquiring-tokens/using-web-browsers) may use. The toolkit does not control Microsoft page behavior or tenant policy. A device-code denial remains a denial; there is no retry using a different identity or auth mode.

## Scope sequencing

1. The first prompt offers Graph device sign-in (default), Exchange device sign-in, or reuse of either provider. There is no manually entered tenant GUID/UPN. Graph bootstrap requests only `User.Read`; Exchange uses `-Device`. The authenticated provider supplies the tenant GUID and account, which the operator must confirm before the menu. No organization/profile API is called merely to discover a tenant name.
2. Every subsequent component must match the confirmed tenant/account; Graph reconnects are pinned to that tenant. Graph-only audit does not require Exchange. Before Audit reads, confirm the exact tenant and organization-wide scope. The selected catalog generates the required read-scope list; unavailable scopes/roles/licensing remain gaps.
3. Before Pull Logs reads, validate all exact targets and the time window, then obtain explicit target approval. Core Graph log sources use approved `AuditLog.Read.All`, `Directory.Read.All` and `IdentityRiskEvent.Read.All`; optional Defender adds `ThreatHunting.Read.All`. These Graph delegated permissions can be tenant-wide even though every tool query is target-scoped. The app does not shrink existing token privileges or certify RBAC.
4. Missing read scopes default to skipped sources. An explicit operator `D` choice requests only the chosen action's supported read scopes; it does not automatically preserve unrelated broad scopes.
5. Source access is validated during collection. Session identity changes cannot silently redirect the next request to another tenant/account. No external tenant writes, broad log fallback, role activation or consent grants are attempted.

Operators must only request access already approved by their organization and must stop at any unexpected consent prompt. This documentation is not permission to grant access.
